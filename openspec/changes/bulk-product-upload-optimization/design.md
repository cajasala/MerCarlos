## Context

The current product master upload endpoint `POST /api/admin/upload-products-csv` parsed in `backend/src/functions/adminBulk.js` performs serial lookup queries for `CategoriaID`, `SubCategoriaID`, and checks existing SKUs for every row. With a large number of products, this creates a major performance issue due to network round-trip overhead.

To fix this, we will implement a staging-table based bulk ingestion strategy, where Node.js streams rows to SQL Server using TDS Bulk Copy (`request.bulk`) and executes a Stored Procedure to resolve IDs and merge records in a single set-based step.

## Goals / Non-Goals

**Goals:**
- Optimize database execution time for large CSV product uploads to complete in seconds.
- Maintain a compatible response format (`{ upserted, errors, message }`) so the frontend and tests do not break.
- Ensure concurrent uploads from different tenants/admins are isolated.

**Non-Goals:**
- Modifying the columns required in the CSV template.
- Adjusting frontend layout or components.

## Decisions

### 1. Staging Table + Stored Procedure instead of JS Chunks
- **Rationale**: SQL Server is highly optimized for set-based operations. Doing validation (joining `Categoria` and `SubCategoria`) and inserting/updating via `MERGE` directly inside SQL Server avoids multiple round-trips.
- **Alternatives Considered**: 
  - *JS Batching (e.g., chunks of 100)*: Still requires O(N/100) database operations. Still significantly slower than set-based execution.
  - *Table-Valued Parameters (TVPs)*: Highly efficient, but requires creating a User-Defined Table Type (UDTT) in the database and configuring TVP structures in Node.js `mssql`. A staging table combined with TDS Bulk Copy is easier to inspect/debug and works out of the box with `mssql`'s standard `.bulk()` capability.

### 2. Multi-tenant Isolation via SessionID + NegocioID
- **Rationale**: In a multi-tenant system, different businesses (`NegocioID`) might upload products concurrently. Using a `SessionID` (UUID generated by Node.js for each request) ensures rows for one upload do not bleed into another. Cleaning the staging records at the end of the SP (and clearing stale rows older than 1 hour at the start) prevents table bloat.

## Risks / Trade-offs

### Risks by Layer

- **Frontend Layer**:
  - *Risk*: A large CSV upload could cause browser request timeout if the backend takes too long.
  - *Mitigation*: The bulk copy and MERGE execution will reduce processing time to 1-2 seconds, far below HTTP timeout limits.
- **Backend Layer**:
  - *Risk*: Node.js process crashes mid-operation after writing to the staging table, leaving orphaned records.
  - *Mitigation*: The stored procedure includes a self-cleaning mechanism at the start, deleting any staging records with `CreatedAt` older than 1 hour.
- **Database Layer**:
  - *Risk*: Concurrent merge operations causing deadlock or constraint violations.
  - *Mitigation*: All operations for a session are wrapped in a database transaction. The merge operates on a sub-query resolved via the specific `SessionID` and `NegocioID`, preventing index lock contention on unrelated products.

### Secrets and Environment Variables
No new secrets or environment variables in `.env` are introduced. The existing database connection config remains unchanged.
